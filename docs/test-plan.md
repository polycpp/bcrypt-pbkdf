# Test Plan

## Unit tests

- `tests/test_pbkdf.cpp`: exercises the public `polycpp::bcrypt_pbkdf::pbkdf` against a set of `(password, salt, rounds, keylen) -> exact key bytes` vectors generated by running upstream `bcrypt-pbkdf@1.0.2` `index.js` (see `## Compatibility tests adapted from upstream` below). Confirms byte-identical output to the upstream JS oracle.
- `tests/test_pbkdf.cpp`: confirms determinism — calling `pbkdf` twice with identical inputs yields byte-identical output.
- `tests/test_pbkdf.cpp`: confirms that mutating one byte of the salt produces a fully different output (no correlated bytes), guarding against accidental no-op state initialization.
- `tests/test_pbkdf.cpp`: confirms thread safety — two concurrent invocations on different threads each produce the correct output; this guards against accidental sharing of the upstream `BLF_J` keystream pointer.
- `tests/test_blowfish.cpp`: exercises the inner `polycpp::bcrypt_pbkdf::bcryptHash(sha2pass, sha2salt) -> Buffer` against a vector generated from the upstream JS oracle (a 32-byte hash output for known 64-byte SHA-512 inputs).
- `tests/test_blowfish.cpp`: confirms that constants `BLOCKS == 8` and `HASHSIZE == 32` match upstream values.

## Integration tests

- `tests/test_pbkdf.cpp`: an "OpenSSH-style" integration test that derives a 48-byte key (32-byte AES-256 key + 16-byte AES-CTR IV) using a 16-byte salt and 16 rounds. This is exactly the parameter shape used by `ssh-keygen` for new-format encrypted private keys; its output is checked against the upstream JS oracle.
- `examples/derive_key.cpp` is built into the test pipeline indirectly: when `POLYCPP_BCRYPT_PBKDF_BUILD_EXAMPLES=ON`, the example must compile and run, which proves the public header surface, the README snippet, and the docs Quickstart all reflect the actual implementation.

## Security and fail-closed tests

- `tests/test_errors.cpp`: `rounds == 0` throws `PbkdfError` with code `InvalidRounds` (matches upstream `if (rounds < 1) return -1;`).
- `tests/test_errors.cpp`: empty password throws `PbkdfError` with code `EmptyPassword` (matches upstream `if (passlen === 0 ... return -1;`).
- `tests/test_errors.cpp`: empty salt throws `PbkdfError` with code `EmptySalt` (matches upstream `if (... saltlen === 0 ... return -1;`).
- `tests/test_errors.cpp`: `keylen == 0` throws `PbkdfError` with code `EmptyKeylen` (matches upstream `if (... keylen === 0 ... return -1;`).
- `tests/test_errors.cpp`: `keylen > 1024` throws `PbkdfError` with code `KeylenTooLarge` (matches upstream `if (... keylen > out.byteLength * out.byteLength ... return -1;` where `out.byteLength == 32`).
- `tests/test_errors.cpp`: `saltlen > 1<<20` throws `PbkdfError` with code `SaltTooLarge` (matches upstream `if (... saltlen > (1<<20) ... return -1;`).
- `tests/test_errors.cpp`: `bcryptHash` with non-64-byte inputs throws `PbkdfError` with code `InvalidHashInput`.
- `tests/test_pbkdf.cpp`: byte-preserving output — the derived key must exactly match the upstream JS oracle for every vector, with no trailing-zero corruption or stride-off-by-one.
- `tests/test_pbkdf.cpp`: every error case is asserted to throw before any output buffer is allocated; the catch block verifies that no partial buffer escapes.

## Protocol/client tests

Not applicable because `bcrypt-pbkdf` is a CPU-only KDF, not a database, cache,
queue, cloud-service, or wire-protocol client. There is no service to back, no
transport mode, no auth flow, no malformed-packet path, no binary type mapping
across a wire, no stateful parser between calls, no listener/server response
writer, no multi-result drain behavior, and no pool/session lifecycle.

## Release-blocking behaviors

- byte-identical output to upstream JS for every recorded `pbkdf` and `bcryptHash` vector
- fail-closed parameter validation: every invalid input throws `PbkdfError` with the documented code, and never produces any partial output
- thread-safety: concurrent `pbkdf` calls on different threads must each return the correct output (no shared mutable Blowfish state across calls)
- the public header set must compile against a fresh polycpp checkout without referring to OpenSSL or `detail/` headers
- examples must compile and produce a runnable `derive_key` binary that matches the README and Sphinx Quickstart snippet
